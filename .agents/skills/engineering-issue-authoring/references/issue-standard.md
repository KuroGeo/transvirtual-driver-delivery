# Issue 编写和拆分标准

## 合理粒度

一个 Issue 对应一个可明确判断通过/失败的结果，例如“离线结果在真实进程重开后恢复”“详情按入口返回原列表”“真机 profile 证明指定工作负载在预算内”。不要把“搭建整个 App”当一个普通执行 issue，也不要为每个类/文件拆一条 issue。

跨多个独立结果时建立 Epic，子项按交付结果划分。模型/数据/UI 的一条小业务链可以同属一个 issue；文件多不等于应该拆分。接口冻结、共享 SDK/依赖和设备租用决定执行顺序。

## 类型差异

| 类型 | 必需信息 | 关闭依据 |
| --- | --- | --- |
| bug | 环境、版本、最短复现、实际/预期、影响、原始证据 | 缺陷路径回归和受影响正常路径 |
| feature | 来源、触发、目标、错误/恢复、范围 | 用户行为及数据合同 |
| engineering | 当前约束、具体改进、消费者/迁移边界 | 产物和可验证收益，不只是“更优雅” |
| verification | 候选版本、验收 ID、设备/数据条件、操作方法 | 对应层级原始记录；blocked 不算完成 |
| release | 目的地/渠道、产物、授权、前置门槛 | 签名/hash、实际回执、需要的现场验证 |

优先级示例：数据丢失、关键业务不可运行、安全边界错误为阻断；其余按用户影响和依赖排序。优先级名称沿用仓库约定，不擅自新建标签。

## 验收句式

“给定条件 → 执行动作 → 观察结果”，附故障/恢复和证据层级。例如：应用内离线，完成 A、失败 B 后真正结束进程，重开仍有原结果与两条原 operationId；恢复测试在线后，匹配确认落盘才移出队列。不得用“代码已提交”“测试都过了”“性能良好”作为唯一验收条件。

## 提交前自审

来源是否存在？目标是否只包含本次范围？依赖是否真实？失败是否可复现？关闭条件是否对齐验证层级？标题和正文是否无需聊天历史？同一 issue 是否混了两个可独立交付的结果？是否复制了凭据/客户/私人邮件信息？

以上是 issue 内容标准，不要求每个 issue 都写长文。小改动可以两段加少量验收条目，保留关键字段。
