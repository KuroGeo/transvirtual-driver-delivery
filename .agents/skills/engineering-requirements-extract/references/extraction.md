# 提取规则

来源不是平级投票：用户当前明确修正优先；当前交互修正文档优于被其替换的旧原型文档；架构负责目标数据一致性与依赖边界。原始题目的特殊要求仅在该交付配置启用，不能替商业版本默认开启 fake、固定位置或测试数据发送。

遇到冲突先写“资料 A 的行为、资料 B 的行为、影响和可选决议”。能够由最新修正解决的直接解决；确需用户决定的保持该边界未冻结，独立任务继续。

提取时检查四种容易遗漏的信息：

- UI 成功反馈对应的是本地 commit、测试确认还是服务端持久接受。
- 返回和切换保留哪些会话状态，进程重开恢复哪些持久状态。
- 初始数据缺字段和新提交必填字段的差异。
- 地图、定位、业务、同步和账号是不同可用性边界。

区分数据样本和业务容量；30 条样本不证明支持数千条。性能预算没有设备/刷新率/工作负载时写为待基线，不能判定性能通过。

项目资料通常含邮件、客户数据或账号信息。提取只保留工程所需字段，不复制私人邮件头或凭据到通用 skill。
