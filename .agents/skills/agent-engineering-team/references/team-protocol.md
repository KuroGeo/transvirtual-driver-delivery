# 工程职能与调度协议

## 职能边界

| 职能 | 输入 | 必须输出 | 不负责 |
| --- | --- | --- | --- |
| 主控/集成 | mission、源码、任务状态 | 有序任务图、派工、集成、门槛判定、可恢复状态 | 用口头汇报代替证据 |
| Harness 工程 | 合同、工具/环境、失败轨迹 | 可执行环境、边界/门禁、观察反馈、恢复和评测证据 | 代写全部产品或自签业务验收 |
| 需求提取 | 原始需求、当前原型、架构、用户修正 | 有来源的需求 ID、行为合同、冲突/缺口 | 自行新增产品方向 |
| Issue 编写 | 需求 ID、缺陷证据、现有 issue | 去重后的工作单、依赖、验收及关闭标准 | 实现功能或自动发布未授权 issue |
| 开发 | 已冻结合同、明确文件范围 | 一条可运行业务链、必要回归、实现说明 | 自签原生/性能/发布验收 |
| 测试 | 合同、实现与失败风险 | unit/widget/integration 测试、故障回归、原始日志 | 为通过测试降低需求 |
| 原生验收 | 合并后候选版本、验收 ID | 设备操作记录、结果/缺陷、证据层级 | 直接改业务实现掩盖缺陷 |
| Flutter 性能 | 设备/容量/预算、候选版本 | 同条件基线、trace、热点、回归数据 | 凭 debug/模拟器推断真机表现 |
| 提交与交付 | 精确候选 SHA、门槛证据、发布授权 | 可复现包、hash、运行说明、真实交付状态 | 把包已生成写成已上线 |

开发者写必要行为测试；测试职能负责独立风险覆盖和故障回归。验收职能从用户流程判断结果，性能职能从设备测量判断预算，三者职责不同。

## 并发策略

用实际运行时能力配置人数。四个 slot 的默认布局：主控 + 两个工作 Agent + 一个测试/审查 Agent。职能是可复用岗位，不要求每个岗位永久占用一个 Agent。

需求冻结前，不让多个开发者各自定义接口。冻结后可并行数据实现、界面实现和测试设计。设备验收与性能共享同一设备时串行；相同设备上的构建、安装、终止进程不能并发。锁定 SDK/依赖、数据库迁移、启动装配、主题/导航和 CI 配置各有单一写入者。

如果工作在同一个目录，派发互不重叠的文件范围；需要跨边界修改时先归还任务给主控重分配。若使用隔离 worktree，先查看已附工作树并复用适合的，记录 base SHA。隔离目录仍不允许双方私自改变同一接口。

## 生命周期

1. **ready**：依赖 accepted；输入可访问；合同版本和文件责任明确。
2. **running**：记录实际 agent ID、起始版本、设备/构建资源租用。
3. **review**：工作 Agent 交回 diff、运行命令、结果文件和缺口。主控审查源码；专职审查者校验对应门槛。
4. **accepted**：判定的需求 ID、验证层级与源码版本都有证据。集成后发现契约变化则重开受影响任务。
5. **rework**：写清复现步骤、实际/预期、影响、负责人，不把修复建议当根因。
6. **blocked**：记录具体外部条件、解除方式、可继续的独立任务。阻塞任务不解锁下游依赖。

同一失败不无限重试。两次同路径失败后让另一职能检查根因；第三次仍无新证据时停止该路径并记录阻塞/待决策。不能删数据、关测试、绕过依赖约束或换服务假装解决。

## 集成与审查

主控只集成任务内变更，不重置用户工作。在候选版本上跑受影响的合同测试；改变共享边界则重新验收消费者。评审结果分阻断缺陷和改进建议：数据丢失、终态绕过、错误确认、关键流程不可运行、授权范围外修改均阻断；不相关重构不阻断当前交付。

任务结束后释放实际 Agent/资源，不因角色列表继续启动空任务。没有可执行 ready 任务时读取阻塞原因或收口，禁止重复规划循环。
